# 真实游戏验收与发布门槛

日期：2026-10-17。**这是待执行的验收规程，不是测试通过报告。** 代码单元测试、合成程序集测试、shell 语法检查不能替代 Steam/Unity/Wine/多人验证。当前真实游戏文件、N5105、外网客户端的结果必须另行记录；未记录者一律未验证。

## 状态与证据

| 层级 | 如何证明 | 通过后允许的表述 |
| --- | --- | --- |
| 静态/合成 | 工具退出码、fixture 和报告 | 工具逻辑通过测试 |
| 构建 | amd64 Docker build 输出、镜像 digest、依赖版本 | 容器镜像可构建 |

| 实战 | Steam 客户端加入、转场、结算、Mod 场景录像/日志 | 该组合在记录场景可联机 |
| 稳定 | 目标硬件 8 小时 soak、性能采样与故障演练 | 该负载通过本次稳定性验收 |

HTTP/进程/端口健康检查只说明对应检查条件；不把 healthy 映射为“玩家可以开始对局”。不得把人工填写的原始 hash 白名单直接命名为“已认证兼容”。

## 顺序验收

1. **文件与补丁前置**：原始游戏放只读来源；输出到独立运行目录。audit 不改源文件。缺少 DLL、未知 hash、签名或模式计数不符时立即失败；输出不应留下半成品。相同输入重复运行应得到可解释、一致的输出和报告；版本检查保留。游戏更新必须得到新的 hash，并重新全套测试。
2. **构建与生命周期**：在 Linux amd64 构建；若在性能更好的机器构建，导入 N5105 后检查镜像架构。全新 prefix 和保留 prefix 分别启动。连续完成 3 次干净 start/stop/restart。`docker stop` 后确认 Wine/游戏/日志进程全部退出；游戏异常退出应体现在容器状态，不能仅剩 tail 存活。失败重启不得无限速循环。
3. **无 Mod 基准**：2 台合法 Steam stable 客户端，先 LAN，然后至少一名外网。客户端与服务器无玩法 Mod。验证正确密码可加入、错误密码拒绝、能选角色和 ready、真正开始 run、伤害/拾取/怪物/玩家状态一致、至少 5 次转场、死亡/复活、结算及下一局。跨版本客户端应正常拒绝，而不是通过伪造版本放行。
4. **Steam 与网络**：分别记录浏览器发现、query、IP connect；其中任何失败不能被另一成功项掩盖。验证两名不同 WAN 客户端可同时连接。至少两条不同运营商/家庭网络。直接 UDP 通过后再按需测 FRP；crossplay/EOS 另列场景，Steam-only 通过不代表跨平台通过。
5. **Mod 分级**：先 BepInExPack/其声明依赖，再必需 R2API 模块，最后每批少量玩法 Mod。确认 chainloader、每个插件、patcher 与内容注册成功且无重复 DLL。每级都重复步骤 3 的实际 run。至少包含一个真正改变网络内容的 Mod 场景；只有 R2API 加载不算 Thunderstore 玩法兼容。负面测试缺依赖、错误版本、缺文件的清晰拒绝与回滚。
6. **4 人长跑**：在 N5105 实际路由负载下连续 8 小时，至少 2 个完整 run，包含后期/高密度场景、10 次以上转场和目标 DLC 内容。空闲 8 小时不能替代带玩家 soak。若 run 自然结束，记录并开启下一局。中途需维护重启则本次 soak 不通过。超 4 人、InfiniteTower/Eclipse 等模式另测，不默认继承 4 人 ClassicRun 结果。
7. **维护恢复**：停止服务，保存旧运行目录/配置/Mod lock/镜像 digest；在新目录更新，失败后恢复旧组合并完成一次加入与转场。`docker restart` 能拉起进程不代表运行中的 run 会保存：未经专门存档 Mod 验证，不承诺断电/重启后续局。确认游戏数据未被自动下载更新覆盖。

## 性能和故障门槛

下列数字是项目建议的验收目标，不是 RoR2 官方保证，也不是 N5105 的测量结果。开服前据玩家地理位置记录可接受的网络预算。

| 项目 | 建议门槛 |
| --- | --- |
| 基础可用性 | 3 次冷启动和所有必要实战场景通过；8 小时无崩溃、OOM、非计划重启、持续异常刷屏 |
| 网络 | 同区域公网直连 RTT p95 ≤ 80 ms、p99 ≤ 120 ms；基准探测丢包 ≤ 0.5%；跨区域单独立预算 |
| 负载抖动 | 正常家用上传/下载并发时，RTT p95 相对空载增加 ≤ 20 ms；达不到则记录带宽/SQM/CPU限制 |
| 内存 | 无 OOM 和持续 swap 抖动；热身后相似场景内存不持续单调增长；峰值至少留 20% 容器限额余量，宿主保留路由余量 |
| CPU/温度 | 无持续热降频或 cgroup quota 节流与事件关联；最忙线程不长时间满核且伴随仿真落后 |
| 同步体验 | 正常网络下无可稳定复现的异常怪物跳位；所有玩家共同停顿 > 250 ms 必须记录定位，不以平均 RTT 合格抹掉 |
| 模拟帧时间 | 仅在真实采集到模拟间隔时评估：p95 计算耗时低于当前实际模拟间隔，并留余量；未采集则标未测，不能用网络 tick 猜测 |

ICMP ping 和 iperf 只检查路径，不代表游戏包丢失率/实际仿真延迟；游戏本身指标、抓包和录像时间线需交叉验证。若没有可用游戏 RTT 指标，明确指标来自 ICMP，不能写“游戏延迟”。正常技能瞬移、出生、传送和有意位置纠正应与异常分开。

在隔离测试网络或独立 Linux 网关用 netem 单变量注入 RTT、抖动和 1% 丢包，检验断连/恢复及行为退化，并保留无损基准。**不要在承担全家 WAN 的生产路由上直接给主接口加 netem。** 客户端掉线重连、服务端丢失 Steam 连接、WAN 短断和磁盘空间不足都应得到可诊断日志；不承诺游戏原生不支持的中途加入或续局能力。
